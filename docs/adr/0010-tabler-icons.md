# Take icons from Tabler, pinned to one version on both clients

`apps/web` takes `@tabler/icons-react` and `apps/mobile` takes `@tabler/icons-react-native`, both pinned to the same exact version, both MIT, both published by the Tabler project itself. A glyph is the outline variant unless a filled glyph carries meaning an outlined one would not, which today means the primary play button and nothing else. Colour is `currentColor` in every case, so an icon takes the colour of the text or control it sits inside and never carries a colour of its own. The mobile app adds `react-native-svg`, installed at the version Expo SDK 57 recommends rather than at whatever is newest. Both packages are imported one icon at a time rather than from the barrel, so no build outcome depends on tree-shaking working. The two are not interchangeable at the version level and must not be: each depends on `@tabler/icons` at an exact pin, and that package is where the geometry lives, so two clients on two releases are two clients drawing different artwork.

The deciding factor is that this is the first icon set whose two runtimes are the same release of the same artwork. ADR 0009 shares values and pure decisions across the clients and duplicates the components, and the specimens had been living with the cost that follows. A throwaway prototype of the header's actions recorded the cost plainly and has since been deleted: the tokens transfer, the drawing does not, so React Native would need its own geometry for the same shapes. Tabler closes that gap rather than papering over it, because the path data both clients draw comes from one pinned package, which is ADR 0009's one source of truth argument applied to artwork instead of to colours. The set also fits the system it is joining rather than needing it adapted: a 24 unit grid, a 2 unit stroke, `currentColor`, and no duotone and no six step weight axis. So the design keeps one weight and never has to invent a mapping between an icon weight and the 400, 500 and 600 type weights, and the glyphs inherit the palette instead of arriving with a colour of their own that would have to be reconciled against the accent.

Four rules hold it together. Outline by default, filled only where filled means something. `currentColor` and nothing else, so an icon can never be the most saturated thing on screen, which the do's and don'ts reserve for album art. One weight, which for this set means the choice between outline and filled rather than a scale. And size from a token scale, not from whatever a component happened to pass: an icon size is a value both clients must agree on, exactly as ADR 0009 reasoned when it added control geometry, so the category list is amended below to carry it. An icon-only control carries an accessible name regardless, because the icon is the affordance and never the name.

What this decision does not settle is the size scale itself. The specimens carry three unrelated sizes today: a 16px glyph in a 32px button, a 22 by 17 shuffle, and a 17px triangle in a 48px pill. Tabler is square on a 24 unit grid, so all three have to collapse onto one scale, and a Tabler glyph does not fill its box the way the hand-drawn triangle did, which means every step has to be measured at its real render size rather than assumed from the grid. That measurement is task `09` work and this record deliberately does not pre-empt it.

Amendment, from task `09`. Three things this record left open are now facts, and one of them is a name nobody could have guessed.

The pin is `3.48.0` for all three packages. It is worth recording that this was checked rather than assumed: `@tabler/icons-react@3.48.0` and `@tabler/icons-react-native@3.48.0` each depend on `@tabler/icons` at exactly `3.48.0`, all three are MIT, and all three are the current release. The lockstep this record argues for is therefore real at this version, and it is the version both clients carry.

There is no icon called `shuffle` at this pin. It is `arrows-shuffle`, and there are two neighbours, `arrows-shuffle-2` and `arrows-random`. `arrows-shuffle` is the one: its two routes run in opposite directions, one left to right and one right to left, which is what a shuffle means, where `arrows-shuffle-2` runs both left to right and reads as a swap. Its heads are open chevrons and not a triangle, so adopting it retires the hand-drawn triangular head that the shuffle prototype spent a long time on. That prototype was good work and it is worth being precise about what it bought, because the answer is not nothing: it is what established that the two heads were merging, that a glyph which is 22 by 17 cannot survive a square grid, and that a filled head has to clear its neighbour. Those are three findings the pin inherits. What it does not inherit is the triangle, because the pin has no triangle to give.

The size scale is `--icon-sm` 16px, `--icon-md` 20px, `--icon-lg` 28px, decided by measuring each step in the control it sits in. The measurement that decided it is that a glyph does not fill its box: across the sixteen glyphs in the system the drawn width runs from 0.17 of the box to 0.93, so a scale read off the grid would have put all of them at one optical size when they are at four. `docs/design/foundations/icons.html` holds the figures.

One consequence is recorded here rather than left to be discovered. The filled play triangle is centred by the set on its optical bounds and not on its box, so it sits 1.5 of 24 units right of centre, which is 1.75px at `--icon-lg` and reads as a triangle pushed to the right of a round button. It is nudged back. That is a position and not a size, so it does not reopen the decision above: the glyph is still drawn at the token size, and both clients still agree on one number per step. Five other glyphs are off centre by half a unit or less. Four of the six off-centre glyphs are corrected; the checkbox tick at half a unit, which is 0.33px inside an 18px checkbox, and the pencil at a third of a unit, which is 0.21px at `--icon-sm`, are left alone on purpose rather than corrected below the threshold where a correction would be invisible anyway. The correction is attached to the `<use>` and never to the element around it, because the two are not interchangeable: play and pause carry identical wrapper markup and differ only in the reference, and a correction on the wrapper centred the triangle and pushed the pause bars 1.75px left of the middle of their own button. That mistake is now a build failure in three directions, so it cannot recur silently.

Amendment, from task `09`, second pass. The play to pause transition became a morph, and it moved two things this record had settled.

**Pause is filled.** It is `player-pause-filled` now, not the outline. The reason is not that a filled pause looks better, which is not a reason the first rule above would accept. It is that the two glyphs are the two ends of one transition, and a transition between a solid triangle and a hollow pair of bars reads as the glyph losing weight halfway through rather than as the shape changing. The endpoints have to agree about ink or the middle is doing two jobs. Measured on the pinned set at 24 units: the filled play is 26.8% of its box and the filled pause 32.2%, a difference of 5.4 points, while the outline pause sits far below the filled play. So the first rule above gains a second case, and the case is not "filled looks heavier" but "filled is one end of a transition whose other end is filled".

**One shape in the system is computed, and this is the exception.** The frames between play and pause are not in the pinned set, because they are not artwork anybody drew. The exception is deliberately narrow and has three conditions.

The endpoints are the pinned glyphs, verbatim. Not a copy of them and not something that resembles them: `player-play-filled` and `player-pause-filled` at this pin, character for character, and the design check fails if either end of the table is anything else. A control at rest is pinned artwork, which is the whole of what this record promises.

The frames between are computed from those two endpoints and never placed by hand. They are derived by `docs/design/scripts/morph-frames.mjs` from the pinned paths' own on-curve points, resampled to a common vertex count and interpolated point for point. A control that is changing is that table; a control that is not is the pin.

The table in the specimen is held to the generator. The strip is literal markup in a hand-written file, which on its own would make it a second source and quietly undo everything above, so the check re-derives the table on every run and compares it against what is in the file. A hand edit to a frame is a build failure, not a divergence. This is the condition that makes the exception safe, and it is the reason the exemption in the drawing-primitive rule is exactly as wide as this check and no wider.

Three invariants travel with it, because a morph has ways of being wrong that a static glyph does not. The gap between the two halves has to open and never close past zero, or the pieces fuse somewhere in the middle. The ink area must not sag more than 3% below where it started, or the shape pinches. The centre must not travel more than half a unit of the 24 unit grid, or a glyph wanders while it changes. Measured at eight frames: gap 0.00 to 2.00 opening, area rising 20% with a 1.4% sag, centre travelling 0.084 units.

The reason the area rule has a ceiling rather than demanding a straight line is worth recording, because the first version demanded a straight line and was wrong. The area of a linearly interpolated polygon is quadratic in the parameter, not linear, so it sags before it climbs. A monotonic rule flags that 1.4% sag, which spread along the outline is under a twentieth of a pixel at `--icon-lg`. The rule that actually earns its place is the ceiling, because there was a real 35% pinch to catch: built with the arc centre on the wrong side and the rotation running the wrong way, every corner of both bars bowed inwards, the pause end measured 25.8% ink against the pinned 32.2%, and the area fell by a third at the midpoint of the transition.

And the reason the area rule exists at all is the second thing that measurement bought. A bounding box is not a sufficient check on geometry here. That same inside-out build had a box within 0.05 units of correct, because the straight edges set the box and the corners do not touch it. Only ink area showed the fault. A check that watches the box would have passed it.

Alternatives rejected:

- Phosphor: MIT, and the strongest artwork of the candidates, which is why it was the first question asked. It fails on the runtime rather than on the design. There is no official Phosphor package for React Native: `@phosphor-icons/react-native` does not exist on npm, and the Phosphor project's own React Native repository has not been touched since May 2023. The maintained option is a third-party package, and its own author measures a single barrel import at 8597 kB against 1876 kB for a direct import, so the phone would also inherit a bundle decision nobody made deliberately. Two clients, two unrelated releases, two sets of geometry.
- Lucide: the same first-party symmetry as Tabler, at a matching version and published days apart, so it was a close second and is the fallback if Tabler ever stops publishing both packages. Rejected on the licence, ISC rather than MIT, and on nothing else. That is a thin margin and it is recorded as one.
- Hand-drawing each glyph, which is what the specimens were doing and what produced a shuffle prototype that has since been deleted. It was working, and that prototype was a good piece of work. It costs a measurement per glyph, which is why a set of sixteen is not obviously wrong to draw, and it cannot give the two runtimes the same geometry, which is the one thing worth buying here. What it did buy is recorded in the amendment above, and it is three findings rather than thirty glyphs: the two heads were merging, a 22 by 17 glyph cannot survive a square grid, and a filled head has to clear its neighbour.
- `@expo/vector-icons`, which ships a Phosphor family already inside Expo and would add no dependency at all. It is a font, so it fails twice: ADR 0009 and `docs/design-system/typography.md` both rule out a second typeface, the specimens already rule out typed glyphs, and a font would leave the web and the phone drawing different artwork, which is the entire problem this record exists to solve.
- An icon font such as Material Icons, for the same reason plus one: the deployment is private and self-hosted, so a font file is another asset to host and another thing to load before an icon can paint.
- A shared SVG path table in `packages/ui-foundation`, so both clients draw from one module of geometry the way they already share tokens. Rejected for the reason ADR 0009 rejects a shared component package. It means hand-maintaining a path table that a pinned dependency already maintains and already versions, and it does not remove the duplication anyway, since the web renders markup and React Native renders through `react-native-svg`, so the two components would still be written twice.
