# Organise the server by four top-level folders, and check the boundaries

`apps/server/src/` is four folders and a `main.ts`: `app/` (the composition root and the request pipeline), `features/` (one folder per domain module), `shared/` (cross-cutting code no feature owns), and `platform/` (the resources features sit on). Each feature holds its own routes, its own service, and its own contracts. Two dependency rules and one lint rule enforce the arrangement, and this record exists because a folder layout nothing checks is a suggestion rather than a structure.

The arrangement came out of a specific failure rather than a taste for tidiness. The rule for who may reach a playlist was written three times, in three feature folders, as three private functions: once as a Drizzle fragment, twice as hand-written raw SQL over the same two tables. Two of the copies even answered differently on purpose, and the comment explaining why took twelve lines. The next feature to need the rule would have written a fourth. A folder per domain module is the right shape for that code, and the right shape is not what was missing: what was missing was somewhere for a policy that belongs to no one feature to live, and a check that stopped the copies. So the cut is four ways rather than fifteen, and the boundaries are rules in `.dependency-cruiser.cjs` and `eslint.config.js` rather than a convention in this file.

The four ways, and the test that separates them. `platform/` holds the database, the config, the media paths, and the job runners, and it has no domain knowledge: a track, a playlist, and an orphan are not words it may use. `features/` holds the domain modules, and a module is a thing a user can do or a thing they own: accounts, playlists, tracks, shares, sync, downloads, prune. `shared/` holds what two or more features need and no feature owns: the context, the problem document, and the access rules. `app/` is the assembly, and it is the only folder that may import every feature, because it is the only place that legitimately knows the whole list. The test is ownership: if a change to it would be described as "a change to how playlists work", it belongs in a feature; if it would be described as "a change to how the app is put together" or "a change to the database", it does not.

Two decisions inside that split are worth stating because they look arbitrary. First, `pruneService.ts` is a feature and `cronJob.ts` is platform, even though they are one job. The service owns the decision that a track with no associations is an orphan, which is a domain claim, and the runner owns when a tick fires and how to stop it, which is not. The same split puts `downloadWorker.ts` in a feature and `intervalJob.ts` in platform, and it is what let the three separate folders for background activity collapse into two modules with a shared `JobHandle`. Second, the health endpoints are in `app/health/`, not in `platform/`, even though they check the platform. `healthRoutes.ts` registers Fastify routes, and the rule that platform does not touch the request lifecycle is worth more than the symmetry of a health check sitting next to the things it checks.

The YouTube adapter is in `AppContext` rather than owned by a feature. It is the instance's single seam to the source, and both features that use it consume that seam rather than own it. It is an interface, which is the point: a test that drives a real app over a fake adapter passes one in, and no feature has to check whether the adapter is present because everything downstream receives a complete context. `AppOptions` keeps `youtube` optional and `buildApp` fills it from config, so the substitution has exactly one seam and it is the entry point.

The rules, and why each is a rule rather than a convention. `platform/` and `shared/` must not import `features/`: a resource or a shared policy that reaches into a feature is a cycle waiting to happen, and it is the shape that put the account row behind the auth pipeline in the first place, with `accountService` importing a type from `auth/`. Only `app/buildApp.ts` may import a route registrar, because a registrar imported anywhere else is a second place that knows which features exist. Raw SQL is confined to `platform/database/` and `shared/access/`, enforced by an eslint selector rather than by dependency-cruiser, because a `.prepare()` call is a member expression and not an import: the schema is the one description of the storage, and a hand-written statement anywhere else is a second one that no migration and no type checks against. Applying the rule removed two statements that did not need to exist. The sync run read was a hand-written `select *` with a rowid tiebreak, which Drizzle expresses with `desc(sql\`${syncRuns}.rowid\`)`, so the ten-field snake_case mapping that existed only to undo what a bare `prepare()` returns is gone, and the property that mapping bought is kept: a new field on `SyncRunSchema` still fails the build, because the Drizzle row would not have it. The two statements that remain are the access rules, where a correlated question about shares would need a join returning a nullable level to be asked through the builder.

Alternatives rejected:

- One folder per feature at the top level, as before: correct for the domain and wrong for everything else. The context, the problem document, the access rules, the database, the config, the job runners, and the two hooks all became top-level folders, so a policy that belonged to no feature had nowhere to go and was written into whichever feature needed it first.
- Folding `platform/` into `shared/`: fewer folders, and the rule "may not import features" stops being a clean slice of the tree and becomes a statement about most of it. The distinction that earns its keep is ownership: `shared/` answers "what do two features need", `platform/` answers "what do all of them sit on", and the prune service is the case where collapsing them puts a domain claim in a folder that has no domain vocabulary.
- Splitting the schema per feature, so each table lives with the feature that uses it: it scatters the storage contract and needs a barrel for `drizzle(sqlite, { schema })`. One 184-line module that every feature imports is the right trade while the schema is one file; the point to revisit is when a table's owner and its reader stop being the same feature.
- A `controllers/` and `services/` split: it spreads one feature across the tree, which is the opposite of the arrangement, and it is the layout the project's own TypeScript guideline already rejects.
- A barrel or index per feature: it hides the module's shape behind one import and makes a cycle easier to create, not harder.
- Enforcing the boundaries with a folder-per-team review convention: the three copies of the access rule existed for weeks under exactly that arrangement. The rules exist because a check that runs on commit is the only kind that survives the next feature.

Consequence worth stating: `createTestContext` lives in `app/testing/`, next to the composition root it builds, rather than in a top-level `testing/`. It is the one non-root module allowed to import `buildApp`, and putting it beside the thing it builds says so without a rule. The dependency-cruiser orphan exception for `(^|/)testing/` still matches it.
