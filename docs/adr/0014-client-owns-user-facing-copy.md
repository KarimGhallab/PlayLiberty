# The client owns user-facing copy, in a shared i18n package

The interface is available in English and French, and the client owns every sentence a person reads. `@playliberty/i18n` is a new workspace package holding the two catalogs, the runtime, the locale resolution, the formatters and the React binding; `apps/web` renders through it and the future mobile client consumes the same package. The server stays language-agnostic: it keeps its English `title` and `detail` as a fallback and returns a stable `code` with structured `params`, and the client maps the code to a message. The runtime is hand-rolled and minimal: `t(key, params)` looks the key up in the active catalog and interpolates `{name}` placeholders, and a plural is selected by a small per-language category function rather than by ICU. The catalogs are typed, `en` defines the `Messages` shape and `fr` is typed as it, so a missing French key is a compile error and the catalog needs no parity test. The keys are symbolic and hierarchical, naming the surface and the fact rather than the English sentence. There is no language in the URL and no server-side locale; the choice is resolved once per browser from an explicit `localStorage` choice, then the browser's preference matched by prefix (`fr-CA` to `fr`), then English, and the document's `lang` follows it.

The deciding fact is that the server has no locale signal. Identity arrives from the Pangolin edge as forwarded headers ([`0003`](0003-identity-via-pangolin-forwarded-headers.md)) and no `Accept-Language` is read, so the server cannot tell what language the reader wants, and copy owned in two places would leave half the sentences in English. Moving the whole sentence to the client gives the words one owner, and a stable `code` with `params` lets the client own them without the server learning a locale. A package rather than catalogs inside `ui-foundation`, because localization is its own concern: the presentation primitives stay free of language ([`0009`](0009-design-system-token-layer.md)), and the package is the seam the phone will consume, so both clients say the same sentence from one catalog. The runtime is hand-rolled for the reason the formatters are: the web client and Hermes must produce the same output, and `Intl` differs by platform, with `Intl.NumberFormat` varying by Android version and `Intl.RelativeTimeFormat` absent there. The cost is owning interpolation and plural selection for two locales, and it is accepted. The typed catalog is what makes a half-translated screen unshippable: completeness is a type error, so there is no parity test and no runtime English fallback for a missing French key.

Two boundaries are worth stating because they are easy to cross. The server's stored failure text (`Track.failureReason` and `SyncRun.error`) is tool output and stays opaque, shown behind a localized label and never translated. User content (playlist names, track titles and account names) is the source's or the user's and is never translated. `ui-foundation` keeps only the presentation primitives language cannot touch (`trackTone`, `sleeveIndex` and the easing curve); the formatters live in `@playliberty/i18n`, `formatDuration` beside the locale-aware ones, so every sentence and every figure the clients draw comes from one place. The whole decision is recorded in [`11-choose-a-language`](../tracker/specs/11-choose-a-language.md).

Alternatives rejected:

- Server-side translation: a second translation store in a process that cannot tell what language the reader wants, since no `Accept-Language` is read and identity is a forwarded header.
- Localizing only the client: the server's `detail` reaches the screen, so a screen would read in two languages.
- Catalogs inside `packages/ui-foundation`: the localization concern would sit among the presentation primitives, which ADR 0009 keeps free of anything that is not a value or a pure decision, and the phone would still need the seam.
- A third-party i18n library (react-i18next, i18next, FormatJS): a dependency and its own runtime for interpolation and two plural forms, when the runtime is a lookup, a `{name}` replace and a two-way category, and the two runtimes still have to agree on the output.
- ICU MessageFormat: a parser and a message syntax for two locales and two plural categories, and the same platform difference it was meant to avoid.
- `Intl.NumberFormat` and `Intl.RelativeTimeFormat`: they differ by platform, so the web client and the phone would say different sentences.
- Natural-language keys, with the English sentence as the key: a copy edit churns the key, and a stale key is invisible.
- A runtime fallback to English for a missing French key: a half-translated screen would ship, which the typed catalog makes impossible instead.
- A per-account language preference: there is no account settings surface, and the choice is per browser.
- A language in the URL, or `Accept-Language` handled by the server: the app is private and not indexed, so a localized URL buys nothing and would double the route table and every link, and the server would still not know the reader.
- A translation service and extraction tooling: the two catalogs are the whole workflow, and a service is another moving part for two locales.
- Locale-aware formatting left in `ui-foundation`: `formatRelativeTime`, the sync state words and the counts depend on language, so they belong where the language is.
