# Push live updates over Server-Sent Events instead of polling

The web client keeps its screens current with one long-lived `GET /api/v1/events` that answers `text/event-stream`. The server pushes an event when server state changes: a sync run starts or settles, a track moves through the download states, a playlist is renamed or deleted, a track is added, removed or retried, a share is granted or revoked. An event is an invalidation hint and never data: it names what changed, and the client refetches the reads it already owns through TanStack Query. A heartbeat keeps the connection open, the client re-reads every query when the stream opens or reopens, and there is no polling interval anywhere.

[`09-keep-the-screens-current`](../tracker/specs/09-keep-the-screens-current.md) chose polling: an interval only while a resource said work was in flight, off once it settled. The conditions were right and the mechanism is what this record replaces. Polling needs a timer per resource, a stop condition read from the last answer, and a request even when nothing changed; the work it watches (a sync, a download, a share revoked by somebody else) already happens inside the server process, so the server knows the moment state changes and can say so. Pushing that moment removes the timer and the request-per-tick, and gives the update when it happens rather than up to an interval later. The client keeps TanStack Query as the single owner of server state, which is the property [`0005`](0005-web-stack.md) chose it for: the stream carries no payload the client renders, so there is no second copy of a server fact.

The transport is Server-Sent Events rather than a WebSocket because the need is one-way and the fit is the platform's own. `EventSource` reconnects on its own, the request is a `GET` so [`0006`](0006-csrf-defense.md)'s client header does not apply, and no second protocol has to be built, secured and tested. The costs are named and accepted: a persistent connection per tab, an edge and a dev proxy that must not buffer the response, an identity checked when the connection opens and re-checked when it reopens, and a test seam for a browser API MSW cannot fake. The bus is in-process because the server is one process; a multi-replica deployment would need a shared bus, which is a change for the day there is more than one replica.

Alternatives rejected:

- Polling, the spec's original plan: a timer per resource, a stop condition read from the data, and a request per tick that usually has nothing to say. It works, and it is the mechanism this record exists to remove now that the server can speak first.
- A WebSocket: bidirectional machinery for a one-way need, a second protocol to secure, and an upgrade the edge must be configured for, with none of `EventSource`'s reconnection for free.
- Long polling, or a hanging `GET` per resource: a timer removed but a request still opened per change, which is Server-Sent Events reimplemented without the browser's own reconnect.
- Conditional requests (`ETag` and `If-None-Match`): they make a poll cheaper, not absent; the client still decides when to ask.
- Refetching only on a mutation, on focus and on reconnect: insufficient. A sync or a download that finishes while the tab sits idle would not move until a person acts, which is the behavior the spec exists to fix.
- Web Push: a service worker and a push service for a foreground SPA, and offline is out of scope in v1.
