# Share design tokens and UI decisions across the clients, not components

`packages/tokens` is the single source of the design values and holds values and nothing else: TypeScript data with lengths and durations as unitless numbers. Its build compiles the package, then runs the emitted emitter, which appends `px` to lengths, `ms` to durations, passes colors through verbatim, and writes a flat CSS custom-property stylesheet into `dist` for the web client; nothing generated is committed, since `dist` is already gitignored. The tokens are flat and carry no `var()` alias: React Native cannot resolve an alias, so an aliased token would reach mobile as a literal string it cannot use, and with a single dark theme there is no re-theming benefit to buy with that cost. The unit lives in exactly one place: the design stylesheet and CSS speak `"8px"` strings, this repository's source speaks the number `8`, and the emitter is the only code that ever adds a unit. `packages/ui-foundation` holds the platform-independent UI decisions and renders nothing; if a module renders, it does not belong in the package. It maps a track's file status and source status to a tone, hashes a playlist id to a sleeve hue and exposes the easing curve; the formatters, and the localization they belong with, live in `@playliberty/i18n`. The tone is the shared decision and its color is chosen per client from that client's palette, so no token value is duplicated across the two. Components are duplicated per client; only values and pure decisions are shared. The design surface is a set of static HTML specimens under `docs/design/` that read one shared stylesheet of custom properties, and `docs/DESIGN.md` and the records beside it in `docs/design-system/` are the committed narrative
record of what was decided. Values reach the repository by transcribing that stylesheet into the package source and reviewing the result as a diff, which is a deliberate manual step rather than an automated extraction, and no value is ever read off a screenshot.

The two clients share no styling runtime: web is SCSS with CSS Modules and BEM over CSS custom properties, and mobile is React Native `StyleSheet` over a typed module. A shared component package would need two implementations of every component and would share only the interfaces, which is the duplication above with an extra package to maintain, while a utility-class pipeline is already rejected on both sides (ADR 0005, ADR 0007). What can be shared is the values and the decisions that do not render, which is why there are two packages rather than one: `packages/tokens` is data plus the emitter, `packages/ui-foundation` is pure functions over that data, and neither imports a renderer. The values must be literal types at build time because mobile consumes the module directly, so emitting CSS from TypeScript serves the web without making CSS the source for mobile. Flat tokens are a consequence of React Native's inability to resolve `var()`, not a style preference, and the single dark theme removes the only reason a web-only alias would have existed.

The contract the design of task `09` must satisfy:

- Dark only, no light theme, per ADR 0005.
- Every text pairing clears WCAG AA.
- A track's sync state is never carried by color alone.
- The five track states are expressible with the token set.
- Every value survives both platforms; nothing that only CSS can express.
- Album art stays the most saturated thing on screen, carried over from the do's and don'ts in `docs/DESIGN.md`.

The token set fixes these categories, with one value per track state, and fixes no value:

- surfaces
- text
- hairlines
- spacing
- shape
- type sizes
- a font family per role, since React Native reads a family name directly and takes no CSS
- motion durations
- a focus ring
- stacking order
- one tone per track state
- control geometry, and the two colours a disabled control needs

Parity between the design stylesheet and the package source is a test rather than a documented manual step, because both now live in this repository and CI can compare them. The design stylesheet is a snapshot of what was decided on a given date and is not a live consumer of the package, so it is never rewritten: a value change is made in `packages/tokens` and re-emitted, and the design file is left standing as the record of the earlier decision.

Alternatives rejected:

- A shared component package: the two runtimes share no rendering model, so every component would ship twice inside one package; the shareable part is the values and the pure decisions, not the markup.
- A utility-class framework (Tailwind on web, NativeWind on mobile): already rejected in ADR 0005 and ADR 0007, and it would still be two pipelines with no shared output.
- CSS-in-JS: DOM-only, so it cannot be the source for mobile, and already rejected for web in ADR 0005.
- A hand-maintained mirror of the values on each platform: two edits per change and no source of truth, which is the drift this decision exists to prevent.
- CSS custom properties as the source, with the typed module generated from them: CSS is not executable data on mobile, and it would make the web's format the source for the phone's values.
- A token file in a third format with a token tool (W3C DTCG JSON and the like): a schema and a toolchain for a small set of values, when the workspace builds with plain `tsc` and has no script runner, and TypeScript already gives literal types.
- Aliased tokens, where one custom property points at another: React Native cannot resolve `var()`, and with one dark theme there is nothing to re-theme.
- Carrying a tone's color in shared code: the tone is the shared decision and the color is the client's, so a shared color would copy one client's palette value into the other.
- A hosted visual design tool as the design surface: one was tried and abandoned. It meters AI tool calls, which puts a weekly ceiling on iteration, and design work proceeds by looking, deciding, and looking again. It also rewrites the literals it stores, normalising hex case and reformatting colours, so its export is not what was entered and cannot be transcribed mechanically, and its style-read API can disagree with its own renderer, so a value read back from it need not be the value on screen. Hand-written HTML specimens have none of those failure modes, cost nothing, are diffable, and are exact by construction.

Amendment, from task `09`: the category list above gained a font family per role. A family is a custom property like any other, it reaches web as `font-family` and mobile as `fontFamily`, and leaving it out would have put the type system somewhere other than the one place every other value lives.

Amendment, from task `09`: the design surface changed from a hosted visual design tool to hand-written HTML specimens under `docs/design/`, after the tool's free tier proved to cap iteration at a hundred tool calls a week. Two consequences. Values now reach the package by a reviewed transcription rather than a tool export, which is slower per change and trustworthy every time. And parity between the design stylesheet and the package source became a test instead of a documented manual step, because both sides are in this repository and no external service has to be reachable from CI.

Amendment, from task `09`: the category list gained control geometry, after task `11` shipped values that fit none of the categories above and left this record contradicting the repository. A control's height, its touch target, the box a checkbox draws in, and the pair of colours a disabled control needs are values both clients have to agree on, which is the whole reason this package exists: if the phone invents a 44px target and the web invents a 40px one, the two platforms disagree about something a user can feel. They are not spacing, because they are the size of a thing rather than the gap between things, and they are not shape, because a radius does not describe them. Leaving them out of the list would have meant the list was wrong rather than the values.

Amendment, from task `09`: rejecting the alias does not mean rejecting a shared value. Two tokens may hold the same literal when they are two names for one decision, and the amber pair is the case that forced the distinction. `--tone-downloading` and `--emphasis` are both `#e39a3c`, because "in progress" and "worth your attention" are near enough in meaning to be one idea and a colour whose name says "downloading" cannot honestly be used to emphasise something that is not downloading. Making one point at the other was tried and is exactly the alias this record rejects, so the two hold the same literal and the validator fails if they ever stop agreeing. The distinction is worth stating because reading "no aliased tokens" as "no repeated values" would rule out the honest way to give one colour two names, and the dishonest alternative is to keep only the narrower name.

Amendment, from `0010-tabler-icons.md`: the category list gained an icon size scale, and the reasoning is the one that added control geometry. A glyph is drawn at a size, and if the phone passes 20 and the web passes 22 the two platforms disagree about something a user can see, which is the whole reason this package exists. The scale is lengths, so it is numbers here and `px` in the emitted stylesheet like every other length, and it is not spacing, because it is the size of a thing rather than the gap between things, and it is not type, because a glyph is not a typeface and carries no advance. The icon set's own grid is not a token: Tabler draws on 24 units, and that is a property of the artwork rather than a decision this repository made, so the tokens are the sizes the design actually uses and not the grid they were drawn on. No value for the scale is fixed by this amendment. The specimens carry three unrelated sizes today and the scale is decided in task `09`, by measuring each step at its real render size, because a glyph does not fill its box and the grid cannot be read off the drawing.

Amendment, from `0010-tabler-icons.md`: the category list gained generated geometry. The play to pause morph is the one shape in the system that is computed rather than pinned, and its frames have to reach both clients, so they are a value in the sense this package exists for: if the phone interpolates between seven frames and the web interpolates between eight, the two platforms disagree about something a user can see, and the disagreement is in the middle of a transition rather than at rest, which is the worst place for it.

It is a category and not an exception to the list because the frames are data, not markup. The morph is eight frames of path data on a 24 unit grid, and both clients draw one frame at a time, so what has to be shared is the table and the frame count, not a component. The strip, the keyframes and the `steps()` timing are each client's own business, exactly as the markup is in every other category: the web steps a transform and React Native steps an index.

The generator is the source, and the table is emitted from it rather than maintained beside it. `docs/design/scripts/morph-frames.mjs` holds the two pinned endpoints and derives the frames between them, `build-morph-frames.mjs` writes the table for this package to transcribe, and the design check re-derives it and compares against what the specimens hold. Three things follow from that arrangement, and each is the reason for it. No frame is ever typed, so the one-geometry argument in ADR 0010 holds for the whole table and not only for its two ends. A change to an endpoint moves every frame with it, so the table cannot drift from the artwork it claims to come from. And the emitted file is reviewable, because a reviewer can read a path table and see the endpoints are the pinned ones.

What is shared is the table and the invariants, not the number of frames being free. Eight frames is a decision and it is recorded in `docs/design-system/icons.md`, but the invariants travel with the table because they are what makes a computed shape safe to share: the gap between the halves opens and never closes, the ink area does not sag past its ceiling, and the centre does not wander. A client that interpolated the same eight frames differently would still be wrong, and these are the conditions that catch it.

Amendment, from task `09`: the category list gained an easing curve, and with it a fourth kind of value for the emitter to handle. A duration is a number and the emitter writes `ms`; a length is a number and the emitter writes `px`; a colour is already CSS and passes through. A curve is none of those. It is four numbers the emitter has to wrap in `cubic-bezier(...)` for the web, and the four numbers themselves are what React Native needs, because `Easing.bezier` takes them as arguments and not as a string. So the source speaks the four numbers, the emitter writes the function syntax for CSS, and `packages/ui-foundation` exposes the mapping to `Easing` as one of the pure decisions it already exists to hold. The unit, or here the function syntax, still lives in exactly one place.

The value is `cubic-bezier(0.4, 0, 0.2, 1)` and it is the only curve in the system. It was added because the form controls had been naming a line height in the curve position of four transitions, which is not a valid easing function, so each declaration was dropped whole and three controls that were meant to move snapped instead. That is the argument for the token existing at all, and it is worth recording that a token was the fix rather than four literals: the four declarations were identical and the mistake was identical, so one shared value is one place for the mistake to be made once and caught once.

The curve is named for the decision rather than for its shape, and it deliberately sits outside the `--motion-*` family, which is all durations. A reader who finds a curve among the durations will read it as a time. The two decorative loops keep the `ease-in-out` keyword rather than this token, and the reason is worth stating because it looks like an inconsistency: a loop is not a transition, and a transition curve applied to a pulse changes the pulse. That is a decision about the two cases rather than an oversight in one of them.
