Add a track

The dialog the playlist detail hosts, on both clients, and its only door for one pasted video. It takes a video URL and a set of writable playlists, and it is one request for the whole batch: POST /tracks resolves the video once and answers one outcome per chosen playlist.

It is named for the track and its field takes a video URL, which is the glossary's own distinction: a track is what the server stores, a video is its source. Drawn as it appears on the playlist detail, with the current playlist preselected.

Choosing, then reporting

The common case, the current playlist checked and one video URL; and the state that only appears when a refusal comes back, with the playlists that refused named by name.

Usage

Do keep the whole batch as one request. Do start the current playlist checked and leave every writable one selectable. Do show already_present as success, because it is. Do name the refused playlists by name and say nothing about the cause, which the route withholds so the batch cannot enumerate other accounts' playlists. Do not disable a playlist the account cannot write to; leave it out. Do not show a report for an all-success batch: the dialog closes and there is nothing to read.

The dialog stays open on any refused and closes only when every outcome is a success, because a refusal is the one outcome that needs attention before the person leaves, and this dialog is the only place that knows which playlist refused.
