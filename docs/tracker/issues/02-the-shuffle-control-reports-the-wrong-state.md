# 02: The shuffle control reports pressed on every playlist

**State:** resolved
**Category:** `bug`

## Observed

Every row in the library draws its shuffle button as a toggle, and every one of them reports
`aria-pressed="true"` and the accent fill the moment any queue is shuffled. Pressing Shuffle on one
playlist turns all of them on.

`PlaylistListItem` reads the player's single global flag and hands it to every shared header:

- [`PlaylistListItem.tsx:61`](../../../apps/web/src/views/library/PlaylistListItem.tsx)
  `const shuffled = usePlayerStore(state => state.shuffle);`
- [`PlaylistListItem.tsx:79`](../../../apps/web/src/views/library/PlaylistListItem.tsx) passes
  `shuffled={shuffled}` for every item.
- [`PlaylistHeader.tsx:457`](../../../apps/web/src/shared/components/PlaylistHeader/PlaylistHeader.tsx)
  `aria-pressed={shuffled}`.

The store's `shuffle` is one boolean for the queue, not a per-playlist fact, so with three playlists in
the gallery all three toggle on together.

## Expected

The control's state is about the playlist it belongs to: a row is pressed only while the queue is that
playlist _and_ shuffle is on, and every other row is unpressed. A screen-reader user must be able to tell
which playlist is playing from the toggles alone.

The alternative, if the press is really "start this playlist, shuffled" rather than a mode toggle, is a
plain action button with no `aria-pressed` at all. The item's own comment says the press starts a queue
from tracks this screen has not read, so the toggle semantics may be the wrong shape to begin with.

## Evidence

- Live, 2026-10-05: seeded three playlists (Focus, Late Night Drive, Evening Jazz), pressed Shuffle on
  Focus, and all three rows turned accent and all three buttons reported pressed.
- `usePlayerStore` exposes one `shuffle` boolean and one current playlist id; the id is already available
  to compare against `playlist.id`.
- Critique run `views-library-librarypage-librarypage-tsx-a51b86be`, Priority Issue P1 (Nielsen heuristics
  1 and 4).

## Agent Brief

**Category:** bug
**Summary:** A playlist row's shuffle toggle reports pressed whenever the player is shuffled, on every
row, instead of only on the playlist the queue belongs to.

**Current behavior:**
Every item in the library draws a shuffle toggle, and each one reports `aria-pressed` from the player's
single `shuffle` flag. The flag is global to the queue, so shuffling one playlist turns the toggle on for
every row, and a screen reader hears as many pressed toggles as there are playlists. The playlist detail
draws the same control from the same global flag.

The design records already name the "forty toggles" as an accepted cost, but they also say the press
"starts the playlist it was pressed on" and is "not a flag toggled on a queue the header does not own".
The code ships the toggle half and drops the per-playlist half.

**Desired behavior:**
A row's shuffle reports pressed only while both are true: the queue belongs to that playlist, and the
player is shuffled. Every other row reports unpressed. The control still appears on every item and still
starts its playlist, shuffled, when pressed; the per-playlist toggle behavior (a second press on this
playlist's own queue turns the shuffle off) is unchanged.

**Key interfaces:**

- The playlist header's shuffle control: its pressed state is the player's shuffle AND the queue belonging
  to this playlist. The header already receives both facts as `shuffled` (the player is shuffled) and
  `current` (this playlist is the queue); combine them for the pressed state rather than reading `shuffled`
  alone.
- The library item: it must tell the header whether the queue is this playlist (`current`). The queue's
  playlist is the queue's own tracks' `playlistId`; compare it to the row's playlist id. The detail already
  passes `current`.
- The design records for the library screen and the playlist header: replace the "forty toggles" cost
  sentence with the rule that only the queue's playlist reports pressed.

**Acceptance criteria:**

- [x] Shuffling one playlist leaves every other row's shuffle reporting `aria-pressed="false"`.
- [x] The shuffled playlist's own row reports `aria-pressed="true"`.
- [x] A second press on the shuffled playlist's own row turns it off and returns `aria-pressed="false"` for
      every row.
- [x] The playlist detail's header reports pressed only while the queue is that playlist and shuffle is on.
- [x] A test covers two library rows: shuffling one leaves the other unpressed.
- [x] The design records state that only the queue's playlist reports pressed.

**Out of scope:**

- Removing the shuffle control from the items, or moving it to the player bar (the record's accepted cost
  stands).
- Changing the shuffle action itself (starting the playlist, the leader rule, the refusal).
- The player bar's own shuffle control.

## Outcome

Done. A row's shuffle reports pressed only while the player is shuffled AND the queue belongs to that row's
playlist.

- The playlist header combines `shuffled` with `current` for the pressed state, so a row the queue does not
  belong to reports unpressed even while the player is shuffled.
- The library item passes `current` for the queue's own row, derived from the queue's tracks' `playlistId`;
  the detail already passed it, so its behavior is unchanged when it is the queue.
- Tests: the header (pressed only with both facts), the library (two rows, shuffling one leaves the other
  unpressed, and a second press turns it off) and the detail (pressed while this playlist is the queue,
  unpressed while the queue is another).
- Records: [`library.md`](../../design-system/screens/library.md) and
  [`playlist-header.md`](../../design-system/components/playlist-header.md) now state that only the queue's
  playlist reports pressed.
