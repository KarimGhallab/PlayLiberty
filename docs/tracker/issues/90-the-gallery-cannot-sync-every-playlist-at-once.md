# 90: The gallery cannot sync every playlist at once

**State:** `resolved`
**Category:** `enhancement`

## Outcome

The gallery head actions row carries one bulk control beside the language menu and the Add button. It reads `Sync all 4 playlists` over the playlists the active filter shows that the account can write, through the existing `canWritePlaylist` rule, less any playlist already `syncing`. Under the Failed filter that means the failed and writable playlists alone, and a read-only share is never counted or posted to. At a set of one it reads `Sync 1 playlist`; at zero it is not drawn.

Where a pointer can hover the control rests as a 36px square around its glyph, at the same control radius as the head row's other buttons, and grows to its left, revealing the words, on hover or keyboard focus. The glyph holds a slot outside the animated grid, pinned to the button's right edge, so it does not move by so much as a fraction of a pixel while the label's edge travels; only the label track and its left padding animate, and the words fade in over the first part of that travel. A touch screen has no hover to give, so there it draws the full pill, and the count is in the accessible name in every state. While the loop runs the control opens itself, since a disabled control cannot be hovered and the progress sentence is the only thing saying the run is going.

A press freezes the ids and posts them one at a time through the existing per-playlist route. A `409` is counted as already running and the loop continues; any other refusal stops it, and the loop's notice names the stop with the refusal's own sentence. The control stays on screen for the whole run of the batch it started, not just for the loop of requests: it holds the batch's count, its spinner and a legible busy state until a list read taken after the loop finds none of those playlists running. Without that it unmounted the moment the last `202` returned, because every playlist it started was already `syncing` by then, and the words flipped back to the idle label for the couple of frames before that read landed. While it reports a run it is disabled but not dimmed, since a run in progress is not an unavailable control. The library is invalidated once when the loop settles, through `everyPlaylistChanged`, so the per-playlist refetches stay the live events' job.

The head row wraps instead of overflowing, so the expanded pill at the phone width, where the Add button becomes a floating action, has a line of its own rather than a cut label. The expand motion is dropped under `prefers-reduced-motion`. No batch endpoint, no aggregate run and no progress count were added, and the per-playlist overflow Sync and the detail header's Sync are untouched.

The new tests cover the control's count, singular and busy state, the fan-out's order and its one invalidation, a `409` carried on and any other refusal stopping it, the filter-scoped count, the read-only exclusion, the absent control at zero, the press-time count under a held request, the tally notice, and the control still being there once the list read reports the batch running.

The press path was driven in Chrome against the built app on a stub API, before and after. Before: the busy label at t=687ms, the idle label back at t=1121ms, and `present: false` at t=1155ms, where it stayed for the rest of the run. After: one state change, from the idle label to `Syncing 3 playlists...` at t=3360ms, present and fully opaque through the run while the gallery moved the three tiles into its Syncing group, never unmounted and never dimmed. Reverting the batch rule alone makes the new test fail at the assertion after the Syncing heading appears, which is the regression it holds.

The collapsed shape was measured in Chrome against the built stylesheet. At rest the button is 35.9 by 36 with a 6px radius, the label box is 0 wide, and the topmost element at its centre is the glyph, so no letter shows through; hovered it is 158.5 wide with the right edge fixed at 1310.17. The glyph sits outside the animated grid, in a slot pinned to the button's right edge, because a column inside the grid inherits the track's fractional rounding and drifted the glyph by 0.7px during the transition. With the slot the glyph's x is 1284.21 in every frame of the close while the width runs 36.7 down to 35.9, and it reads 9.96px from either edge at rest. Under a touch-emulated 390px viewport `(hover: none)` matches, both buttons are 158.5 wide with the words out, and the row does not scroll.

Two traps the next change has to respect: a gap inside the clipped label claims its own width and leaves the first letter showing at rest, so the gap is the reserved right padding; and `right` on an absolutely positioned child is measured from the padding box, not the border box.
