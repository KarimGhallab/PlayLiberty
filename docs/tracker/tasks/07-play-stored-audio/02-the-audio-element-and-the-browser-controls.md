# 02: The audio element and the browser controls

**Blocked by:** [`01`](01-build-the-queue-and-play-it.md).
**Status:** resolved

## Outcome

Implemented and verified against real stored audio in a real browser.

**Seeking needs a separate signal from reporting.** `positionSeconds` is written by the element on every `timeupdate`, so it cannot also mean "the person asked to move": an effect that applied it whenever it changed would fight the element's own progress. The store gained a transient `seekTo`, written once by `seek(seconds)` and cleared by the element after it applies the value. This is the mechanism the ticket's "sets the element's position rather than waiting for the file" actually requires, and it is the one piece of state that is neither persisted nor a plain mirror of the element.

**Resuming at an offset waits for metadata.** `currentTime` cannot be set before the browser knows the file's duration; setting it earlier is silently dropped and the track starts at zero, which is the bug the previous scaffold had. The element records the store's `positionSeconds` in a ref at the moment a track is reached and applies it on `loadedmetadata`. It is a ref and not an effect on `positionSeconds` for the same reason seeking has its own signal: the value is a fact about when the track was reached, not about the current render.

**The end of the queue is a different answer from skipping at the end.** `skipNext` at the last track does nothing, while `advance` (what a finished track calls) stops playback and resets the playhead, so finishing the album stops rather than looping. The two are separate actions because they share the move and differ at the boundary.

**Volume became part of the persisted state.** The ticket says the volume is stored and applied, so `PersistedPlayerState` gained `volume`, and the read normalizes it to the default when absent rather than discarding a payload written before the field existed. A malformed volume still fails the read, so the leniency is about one missing preference and not about types; a test covers both.

**The Media Session lives in its own module behind a shape check.** `mediaSession.ts` feature-detects by checking for a usable `setActionHandler` rather than the mere presence of the key, because a partial implementation can carry the key with nothing under it; presence was the previous guard and it is the reason a stub could crash the player. Each action is registered inside its own `try`, so an engine that rejects one action still receives the others instead of losing the whole session to a single throw. Metadata and handlers are re-published whenever the track changes, so the controls never describe a track that is gone.

**The artwork is the thumbnail route, made absolute.** The first cut passed `thumbnailPath` straight into `artwork`, which is wrong twice: `thumbnailPath` is `thumbnails/<shard>/<videoId>.jpg`, a path under the server's media root and not a URL, so as `artwork.src` it resolved against the app origin and 404'd; and the media session resolves `artwork.src` in its own context rather than the document's, so the URL has to be absolute. The artwork is now `new URL('/api/v1/tracks/<id>/thumbnail', window.location.origin).href`, carved from the track id the element already holds. The route is authenticated and fails closed on Pangolin's `Remote-*` headers, so an engine that fetches the artwork outside the page's session gets no image and falls back to a generic one; that is a missing picture rather than a broken player. Verified with the identity header: the route returns a real `image/jpeg`.

**The album is the playlist name, carried on the queue entry.** The album said `PlayLiberty`, which named the app rather than the source. The name belongs there, but the queue entry carried only `playlistId`, and the media session resolves in a context that cannot fetch, so a name looked up at play time is a name missing after a relaunch. `PlayerTrack` gained `playlistName`, persisted alongside the id, and `toPlayerTracks` stamps it once when the queue is built. The read that supplies it is a new `GET /playlists/:id` consumed by `usePlaylist`, separate from `usePlaylistTracks` because the name belongs to the playlist and not to any track. A stamped name goes stale on a rename, which is accepted: the queue is a snapshot of what was played, and ticket 04's bar reads the same field for the same reason.

**What the browser proved that the fake cannot.** Against the real instance: the element played through `/api/v1/tracks/<id>/stream` with the duration read from the file; a full reload restored the queue and resumed the element at the persisted 45.09s offset with nothing autoplaying; `seek(150)` moved `currentTime` to 150 immediately and playback continued from there, with the request clearing itself; skip stopped at both ends; ending the last track stopped rather than wrapping; the session metadata followed the track; and the network log held the tracks read and the stream requests and nothing else, with the second track requested only when it was reached rather than prefetched.

Tests: thirteen added to `playerStore.test.ts` (transport moves one place and stops at both ends; the end of the queue stops rather than loops; advancing on a finished track; skipping resets the offset; pause and resume keep the place; `seek` writes the position and raises the request, clamps at zero, and a reported position raises no request; volume clamps and refuses a non-number), five added to `playerPersistence.test.ts` (volume round-trips; a payload without volume is kept and defaulted; hydrate restores the volume), a new `mediaSession.test.ts` (metadata publishes and clears, an absent API is inert, a throwing constructor is swallowed, every action routes, one rejected action keeps the others, an absent teardown is inert) and a new `PlayerAudio.test.tsx` (the source is derived from the id and one element exists, a track change replaces the source without adding an element, pause and resume keep the place, the persisted offset is applied on metadata, a seek moves the element and clears the request, the volume reaches the element, ended advances then stops, a refused autoplay clears the playing state, the artwork is the absolute thumbnail route for a track that has one and empty for one that has not, and an absent Media Session does not throw). jsdom has no media pipeline, so the element is stubbed at `HTMLMediaElement.prototype.play`/`pause` and driven by real events rather than replaced. The detail page's read of the playlist name is covered by a heading test and by the queue carrying the name.
