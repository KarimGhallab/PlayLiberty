# 03: Add a playlist from the gallery

**Blocked by:** [`02`](02-an-empty-gallery-not-an-empty-playlist.md).
**Status:** resolved

## Outcome

Implemented and verified. The dialog is `AddPlaylistDialog.tsx` under `src/views/library/`, view-local for the same reason the gallery is: the library is its only host. It is the `400px` card on `--surface-raised` the design settled, with the one `Playlist link` field, `Cancel` and `Add`, and the invalid and working states the design also settled.

The client grew its mutation half. `client.ts` now has `apiPost`, which sends a JSON body, reuses `send` so the `X-PlayLiberty-Client` header is attached by the same code every mutation goes through, and parses the reply with a schema. `queries.ts` now has `useCreatePlaylist`, whose `mutationFn` posts the URL and whose `onSuccess` invalidates `['playlists']`. The route answers `202` with the `SyncRun`, not the playlist, so the hook parses a `SyncRun` and writes no optimistic row: the new item is the server's, and it arrives on the read the invalidation triggers, already `syncing` because `startSyncForSource` writes that state before the route answers.

The client refuses empty and malformed URLs with `CreatePlaylistInputSchema.safeParse` before the mutation, which is why no request is made. The server's `400 invalid_request` carries `detail`, and that `detail` is what the field shows when a create is refused; while a server problem stands it is the whole message, and typing clears it. Both the header's labelled control and the gallery's action open the same dialog, which is the design's two placements of one control. On success the dialog closes and the person stays on the library, watching the new playlist appear rather than being routed into it.

The dialog fades in and out over `--motion-base` on `--ease-standard`, the scrim by opacity and the card by opacity and a 98% to 100% scale. The exit names its own keyframes rather than reversing the entrance, because a finished animation whose direction changes is re-resolved at its end value instead of restarting, so a reversed keyframe produces no visible exit; the bug was found and fixed in the browser. The node outlives the open state so the exit is visible, and a timer at that same duration unmounts it rather than `animationend`, which a suppressed animation or a non-compositing environment may never fire; the duration is handed to the stylesheet as `--dialog-motion` so the animation and the unmount cannot drift. A reduced-motion reader skips the wait. The design rationale is recorded in this ticket.

One design point worth recording: `LibraryPage.test.tsx`'s empty and failed-read cases had asserted on `getAllByRole('button', { name: 'Add a playlist' })` now that the header carries the control in every state. The empty-gallery case expects two (header and gallery, which is the design), and the failed-read case asserts on the absent gallery promise rather than on an absent button, because the header's control is chrome and stays.

Tests: eight in `AddPlaylistDialog.test.tsx` (focus on open, empty refused, malformed refused, valid submit trimmed, server problem beside the field, busy refuses a second submit, cancel, axe) and five added to `LibraryPage.test.tsx` (one dialog from either control, a valid submit posts, closes and stays, the new item arrives as `Syncing`, an empty URL makes no request, and a refused create shows the server's `detail`). The two success/refusal cases override the `GET /playlists` and `POST /playlists` handlers through MSW; the list override returns the base playlist until the create has happened, so the read before the create cannot see the new item and the assertion is about the server's row arriving, not a client guess.
