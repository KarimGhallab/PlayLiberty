## Design Specificity Verdict

**Verdict: authored for this product, not category-interchangeable.** The vocabulary is PlayLiberty's own: five file-status tones plus a removed source, the "2 tracks are not stored" badge with its per-state breakdown, the sync band, the skip-non-music switch, and copy that states the product thesis directly ("All N tracks are still here and will never be deleted even if the video is removed"). A generic player could not carry any of it unchanged.

**LLM assessment.** The three header arrangements share one seam (`usePlaylistHeader`), so their facts cannot drift, and the same playlist keeps its derived sleeve hue across gallery and detail. The structure is coherent. Two things blunt the specificity: the shipped gallery contradicts its own design record, and the accent, briefed as "spent once per screen", is spent on nearly every control that can be acted on.

**Deterministic scan.** `impeccable detect --json apps/web/src` returned **0 findings, exit 0** across all 142 files. This is a real clean, not a suppressed one: `--no-config` also returns `[]`, and no ignore config exists. The detector's CLI path is regex over non-HTML files and `apps/web/src` ships no `.html`, so layout-dependent checks are structurally invisible to it. That makes the browser pass the load-bearing one, and the browser pass disagrees with the CLI.

**Visual overlays.** Injection preflight succeeded (title mutated, script appended), the overlay server ran and was stopped afterwards (`live-server stop`, port 8400 verified unreachable). In the page, the detector reported the same class on every instance: `_playlist-header__name-text_` (the playlist name link in `PlaylistHeader.module.scss`) overflows its box, by 58px on desktop, and up to 152px at narrow widths, with 9 overflowing instances in the narrow pass. This is the intended ellipsis truncation, so the CLI's silence is not a false negative of the same claim. Two 404s for missing thumbnails also appeared on every load, one per playlist whose every download failed. No JS exceptions, no React warnings.

## Overall Impression

This is a high-craft, unusually disciplined interface. The theming system does what its document claims (single literal source, derived sleeves, tone-not-colour states, one reduced-motion owner), and the copy states the product's actual promise at the moments it matters. The failures are not sloppiness; they are three places where one screen and another disagree about the same fact, or where the same fact is hidden. The single biggest opportunity is coherence: the detail page is where the product's promise is decided, and it is the weaker of the two screens.

## What's Working

1. **Row-state language.** Every tone carries a word, a failure carries the server's own sentence kept secondary and ellipsized, and a removed source takes the removed tone over its file status. Verified on the Failed row (red word and reason, hatched art, no play layer) and the Removed row (muted word, unplayable, lane retained). Colour is never the only channel.
2. **The sleeve fallback.** A hue derived from the playlist id, one lightness and chroma, skipping the accent's green and the amber/red the states own, under a hatch. Deep Focus, Empty Mix and Rainy Sunday read as one family meaning "no artwork", never as a state, and the hue survives the gallery-to-detail move. Nothing is stored.
3. **The three arrangements as markup over one seam.** Row, card and tile are separate modules sharing one hook, and the phone card's 32px controls grow 44px targets through boxes that paint nothing. The phone gallery genuinely looks designed, not shrunk.

## Priority Issues

**[P0] The detail hero play is a dead action when nothing is playable.**
- **What**: On a playlist whose downloads all failed (Deep Focus, 4 tracks, 0 stored), pressing the 48px hero play on the detail page does nothing at all: no toast, no state change, no message. The source confirms it: `PlaylistDetailPage.startFrom` calls `startPlaylistQueue(...)` and discards its boolean, while `useStartPlaylist` turns the same result into a refusal notice. The detail consumes `refusal` for shuffle only.
- **Why it matters**: The primary control of the detail silently no-ops in exactly the situation the product exists to make legible, while the identical control in the gallery explains itself. Users conclude the app is broken.
- **Fix**: Route the detail's play through the same refusal path so the dead press produces the gallery's notice.
- **Suggested command**: `/impeccable harden`

**[P1] The filter chip rail hides a chip at every desktop width.**
- **What**: On the detail at 1440, the chip container is 563px wide with `scrollWidth` 692, so the `Unavailable 1` chip is clipped at x 1096-1228 and the sort control sits beside a half-pill. `scrollbar-width: none` and no edge fade or chevron, so the rail looks complete. The phone is worse: a pill is cut mid-word.
- **Why it matters**: The state a user most needs to act on, a track removed from YouTube, has an invisible filter. The design record calls sideways scrolling a decided feature, but a filter you cannot see is not a filter.
- **Fix**: Add an overflow affordance (edge fade plus a scroll hint), or wrap the chips at desktop widths where room exists.
- **Suggested command**: `/impeccable layout`

**[P1] The identity count silently changes meaning when a filter is on.**
- **What**: Filtering Evening Jazz to `Failed 1` makes the identity card read "1 track" with no qualifier; `Pending 0` makes it read "0 tracks", while the chip rail reads "All 8". `countTotal` is the filtered total, so the `{shown} of {total}` path cannot trigger.
- **Why it matters**: Two facts on one screen contradict each other and the card looks like it lost seven tracks. It reads as data loss in a product whose whole promise is that nothing is lost.
- **Fix**: Keep the playlist's own total in the identity block and put the filtered figure on the rail, or qualify the count.
- **Suggested command**: `/impeccable clarify`

**[P2] Two disagreeing "failed" numbers on one screen.**
- **What**: On Deep Focus the sync band reads `0 kept / 4 added / 0 removed / 0 failed` while the chip rail reads `Failed 4` and all four rows read Failed. The band describes the last run, the rows describe current file status, and the shared word hides the difference.
- **Why it matters**: The user cannot answer "is anything broken?", and the reassuring "failed 0" actively misleads.
- **Fix**: Label the band as this run's summary, or suppress an all-zero band.
- **Suggested command**: `/impeccable clarify`

**[P2] The same "nothing playable" condition draws two different affordances.**
- **What**: Empty Mix (0 tracks) draws a disabled play button; Deep Focus (4 tracks, 0 stored) draws an enabled one that can never play. Playability is computed from `trackCount`, not the stored count.
- **Why it matters**: A disabled control is honest; an enabled dead one erodes trust, and it is the same real condition.
- **Fix**: Base playability on the stored count so both disable, and let the badge carry the reason.
- **Suggested command**: `/impeccable harden`

## Persona Red Flags

**The household curator (desktop, daily operator).** Opens Deep Focus after a bad sync: the big green play does nothing; the left column says "Up to date", "4 tracks" and `failed 0` while four red rows say Failed; to retry the four failures he must open four separate row overflows because Retry is per-row and "Fetch whole" is unexplained; to find the removed track he reaches for the `Unavailable` chip and it is off the clipped rail.

**The reader on the phone (Casey, one-handed).** On a detail page the sticky header is roughly 230px tall over 844px, so with the 98px player bar and the FAB about 500px of list remains and does not recover while scrolling. On the gallery the pinned playlist he wants truncates to "Evening J..." on the card, and `title` is unrecoverable by touch. The metadata line ("8 tracks", "Up to date") is `--text-xs` muted, which is hard one-handed in daylight.

**The keyboard-only operator (Sam).** The menu contract genuinely holds: a row's focus ring paints around the whole row, ArrowDown opens the overflow onto its first item, Home/End and Tab behave, Escape returns focus. What breaks: the disabled chip rail and the disabled sort give no reason, only a dimmed state; and each row's lane control grows a 44px invisible box that overlaps the trailing part of the row's own play layer, so "play this row" and "actions for this row" are adjacent rectangles with nothing drawn on the row to separate them.

## Minor Observations

- The incomplete badge lives in the actions row on the desktop tile and at the end of the name row on the phone card: two positions for one mark.
- The accent is spent on the detail on the filled Add a track, the hero play, the ON switch, the selected chip, the sort's open rule, the seeker and the volume fill, against a document that reserves it for the play control.
- `DESIGN.md` says the web library tile is "a wide tile with the cover beside the identity". Measured at 1440 the tile is 252x396 with a 236x236 square cover above the identity. The cover-beside-identity arrangement exists in code but is used only as the phone detail header. The design record describes a shape that ships nowhere.
- Every playlist whose downloads all failed issues a 404 for its thumbnail on every load (two per page here). The sleeve fallback covers it visually; the console noise remains.
- The player bar renders at 98px while both pages reserve 97px, so about 1px of the last row hides under it.
- There is no language control on the detail page, so a deep-linked user must return home to switch.
- Both add dialogs clip their own placeholder text.
- The row overflow (Retry / Fetch whole / Remove) puts the destructive item adjacent with no rule, while the playlist overflow inserts one.

## Questions to Consider

1. `DESIGN.md` warns that a previous design record "came to describe a product that no longer existed", then describes a web library tile that exists nowhere in the build. Which is the product, and what else in that file is describing the past?
2. The accent is "spent once per screen: the play control", yet one detail screen spends it on at least six things and the loudest is a filled Add button. If everything is the action, what is the action?
3. Is a filter you cannot see a filter?
4. A run that added four tracks and failed all four reports "failed 0". What is that number for, if not this?
5. Deep Focus's play is enabled and Empty Mix's is disabled, and both play nothing. Which one did the user mean?
