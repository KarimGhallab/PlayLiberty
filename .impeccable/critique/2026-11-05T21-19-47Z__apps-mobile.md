## Overall Impression

The craft keeps improving and the product message got worse. Four of the last run's gaps are genuinely closed: sync is one press from the state it changes, the typeface loads, the gallery card is one accessibility stop, and a removed-but-stored track now has its own count and filter. Then the new chip reuses the exact string that marks a lost track (`removedFromChip` and `removedFrom` are the same words), so the screen that proves the promise is the screen that erases it. The single biggest opportunity is to let the row say two things at once: what the file is, and what the source is.

## What's Working

1. **The retention message now has a shape.** A pink retained role, a count that sits beside the buckets rather than inside them, a filter, a card line, and a sentence in the sheet. The mechanism is right and the copy inside the sheet is the best writing in the app. Only the row and chip words fail it.
2. **The detail header is one object.** Cover size, identity width, action row and backdrop all interpolate from the same progress value, and the wide and compact states hold four lines without a reflow (`PlaylistIdentity.tsx:490-541`). The gesture follows the finger and runs backwards.
3. **Undo is a real window, not a toast.** Delete and remove hide the row, open six seconds with "More time", hold the commit behind a grace period and keep the back gesture until it closes (`PlaylistDetail.tsx:1037-1101`). Sign-out now arms an in-place confirm instead of firing (`AccountSheet.tsx:191-230`).
4. **The accessibility floor is built.** Every detail control has a name (24 of 24), effective targets reach 48dp through `hitSlop`, the card is one stop with its actions attached, there are no hardcoded user strings, English and French have 359 leaf keys each with zero difference, and every text pair clears 4.5:1 (worst 4.60:1).

## Priority Issues

### [P1] The word for a track that survived is the word for a track that was lost

**What:** `trackStateLabel` returns "Removed from YouTube" whenever the source is gone, before it looks at the file (`packages/i18n/src/formatters/formatters.ts:110-124`), and `TrackRow` prints it as the only state word (`TrackRow.tsx:74-90`). The retained chip uses the same string by design: `removedFromChip` and `removedFrom` are both "Removed from {provider}" (`en.ts:450-459`). So filtering to the retained view shows "Alaska / Removed from YouTube" (`a-detail-removed-filter.png`), and filtering to Unavailable shows four "[Deleted video] / Removed from YouTube" rows in the same grammar (`a-detail-unavailable.png`). `DESIGN.md` currently mandates the erasure: a removed source takes the removed tone whatever the file says.

**Why it matters:** This is the one screen where the household member checks whether a removal cost them anything, and it cannot answer. The chip counts 1 and 4, the rows say the same words, and the survival evidence sits in a sheet behind the "..." door. The app tells the user what happened to YouTube and stays silent about what happened to their music at the exact moment it is asked.

**Fix:** Give the row two facts with the file first: "Still stored" in the retained role, then "Removed from YouTube" as the second line, and give the unavailable row a sentence saying it was already gone before the first sync. Give the chip its own word ("Removed, still stored" or reuse the sheet's phrasing), and update the DESIGN.md rule that mandates the erasure. The `meta.retained` copy already exists as the right register.

**Suggested command:** `/impeccable clarify`

### [P1] Every count describes the playlist, not what survived it

**What:** `incompleteOf` folds terminal `unavailable` into the same missing count as pending and downloading and draws it with `IconDownload` (`PlaylistCard.tsx:91-102`, `240-256`). On Chine all four are terminal, so a 94%-healthy playlist carries a permanent download marker that can never resolve (`a-lib-01.png`). The error band repeats the mistake with a stronger claim: `syncError.safe` says "All {count} tracks are still here" using `playlist.trackCount`, the association count (`SyncBand.tsx:79-86`), on a playlist where four were never stored.

**Why it matters:** One surface implies work in progress that will never finish; the other states something false. Both are the app's reassurance voice, and the reassurance is only as good as its arithmetic.

**Fix:** Split `missing` into actionable (pending, downloading, failed) and terminal (unavailable). The terminal line takes the muted role, no icon, and its own words: "4 tracks were already gone and were not stored". The error band counts stored tracks, not associations, or drops the "all" and names what is safe.

**Suggested command:** `/impeccable clarify`

### [P1] The player bar breaks at 200% text, and it is the only persistent chrome

**What:** `PlayerBar.tsx:772,784,791` and `SeekBar.tsx:202` set fixed `lineHeight` values (19.2dp for a 16pt title, 16.2dp for 12pt) with no `maxFontSizeMultiplier`. At `font_scale 2.0` the 32pt title sits in a 19.2dp box and overlaps the meta line; the queue position and both seek times collide (`crop-bar-2.0.png`). The same fixed-lineHeight pattern is drawn in `Notice.tsx:287,293`, `AccountSheet.tsx:353`, `EgressScreen.tsx:569,582`, `TrackRow.tsx:333,350`, `SyncBand.tsx:318`, `Screen.tsx:117` and `LibraryHeader.tsx:87`, where the 40pt brand sits in a 24dp box.

**Why it matters:** The bar follows the user across every route. At a large Android text size it is the interface, and it is unreadable. `PRODUCT.md` promises Dynamic Type with a capped multiplier only where a fixed layout would break; this is exactly that case and the cap is missing.

**Fix:** Cap the bar's text at 1.3 and derive its font sizes from the scaled value, or let the bar grow a line. Then sweep the fixed-lineHeight list above and either scale the line height with the font size or set an explicit cap per control.

**Suggested command:** `/impeccable adapt`

### [P1] The gallery stays in the accessibility tree behind the playlist sheet

**What:** The detail route uses `presentation: 'transparentModal'` (`app/_layout.tsx:79-87`) and draws only a scrim (`PlaylistDetail.tsx:738-752`) with no `accessibilityElementsHidden` or `importantForAccessibility="no-hide-descendants"` on the gallery. A single settled dump contains 56 clickable nodes spanning both screens, including "VPN settings", "Account" and "Library actions" at the same time as "Play this playlist" and the track rows.

**Why it matters:** A screen-reader user can focus and fire the library's floating add, its header doors and its filter segments while a playlist covers them. The visual scrim says the page is gone; the tree says it is present, and the two disagree in the wrong direction.

**Fix:** Hide the library subtree while the detail route is focused, and restore it on pop. The player bar should stay reachable, as it is the transport.

**Suggested command:** `/impeccable audit`

### [P2] The status rail hides its own selection, and with it the retained view

**What:** `GalleryFilterBar` reveals a chip only after a user picks one: `restored.current = activeStatus !== null` leaves the default selection unrevealed (`GalleryFilterBar.tsx:102-106`, `146-152`). At 1.0 the default "All tracks 1275" is cut mid-count on first paint (`a-lib-01.png`); at 2.0 the whole status rail is off-screen behind the scope pair (`a-scale2-lib.png`). The detail's rail behaves the same way, and the retained chip sits last, so the product's new proof is the farthest chip from the start.

**Why it matters:** The rail is the only way to narrow a 639-track playlist and the only route to the retained view. A clipped default reads as a bug, and at large text a low-vision user has no discoverable sign that filters exist.

**Fix:** Reveal the default chip once on first measurement, shorten the default label to "All 1275", and at large text moving the scope pair to its own row so the status rail keeps a visible edge. Consider ordering the retained chip after All rather than last.

**Suggested command:** `/impeccable adapt`
